## 3 S4 资金并发压测

### S4-a 500 个任务并发结算

| 指标 | 结果 | 判定 |
|---|---|---|
| 任务数 / 工作线程 | 500 / 64 | — |
| 结算成功 | 500 | PASS（每个恰好一次） |
| 异常数 | 0 | PASS |
| **死锁次数** | **0** | PASS |
| 耗时 | 2619 ms | — |
| 结算 TPS | **≈191** | 记录值 |
| 跑腿实收 | 950000 分 | = 500 × 1900 |
| 平台佣金 | 50000 分 | = 500 × 100 |
| 金额守恒 | 950000 + 50000 = 1000000 | PASS（一分不差） |
| 资金总额守恒 | 压测前后 `SUM(available+frozen)` 相等 | PASS |
| 三层对账 | L1/L2/L3 全过 | PASS |

死锁 0 比预期乐观。托管账户与佣金账户是两个热点行，500 次更新全部落在同两行上，原以为会出现 `Deadlock found when trying to get lock`。没出现的原因是每个事务里对这两行的更新顺序完全一致（先托管户扣减、再跑腿贷记、最后佣金贷记），不存在交叉加锁——**死锁的必要条件是加锁顺序不一致**，顺序统一的批量更新只会串行等待，不会死锁。这一条值得记住：热点行会拖慢吞吐，但不必然造成死锁。

## 4 事务陷阱：六种失效场景全部被证实

每个陷阱都是"错误写法不回滚 / 正确写法回滚"成对断言，不是文档描述。

| 陷阱 | 错误写法结果 | 正确写法结果 |
|---|---|---|
| 同类自调用 | 数据残留（事务失效） | 回滚 |
| 非 public 方法 | 数据残留 | — |
| 异常被 catch 吞掉 | 数据残留 | `setRollbackOnly()` 后回滚 |
| checked 异常未声明 rollbackFor | 数据残留 | 声明后回滚 |
| 手动 new 绕过容器 | 数据残留 | — |
| MyISAM 引擎 | 数据残留（并已断言表引擎确实是 MyISAM） | — |

MyISAM 这条额外查了 `information_schema.TABLES` 确认引擎，避免"以为建成 MyISAM 其实是 InnoDB"的假验证。

### 连接池死锁复现

池 = 2、并发 4 个"REQUIRED 内嵌 REQUIRES_NEW"：

| 轮次 | 成功 | 连接耗尽 |
|---|---|---|
| 第一次 | 0 | 4 |
| 第二次 | 1 | 3 |

两轮结果不同，说明这个竞态本身带随机性——谁先抢到第二个连接取决于调度。所以断言写的是 `exhausted > 0` 而不是固定值，否则测试会间歇失败。**给竞态类测试写断言时，只能断言"必然性"，不能断言随机结果。**

正确配比：`池大小 >= (1 + REQUIRES_NEW 嵌套层数) × 预期并发`。本项目一层 REQUIRES_NEW（资金审计），池 20，安全并发上限 10。

## 5 本期发现并修复的缺陷（3 处）

### 5.1 P1 遗留的资金模型缺陷：同一笔钱被记两次

- 现象：托管账户流水净额 78900 分，快照却是 0；发单人账户流水净额 -78900，快照总额未变
- 根因：P1 的托管同时做了两件事——发单人 `available→frozen`（冻结语义）与托管账户 `available+=`（转移语义）。结果全局 `SUM(available+frozen)` 凭空增加，且发单人账户总额不变却记了一笔 DEBIT 流水，"快照 == 流水净额"直接不成立
- 修复：区分清"托管（担保交易）= 转移"与"冻结（预授权）= 不离账"。本项目做的是托管，一律用转移模型：`casFreeze` 改名 `casDebit` 且只减 available，`WalletAccount.freeze` 改为 `transferOut`/`transferIn`
- 连带修正：`PublishEscrowIT` 的断言从"frozen == 1500"改为"frozen == 0 且托管户 available == 1500"；并按流水净额修正了存量数据的账户快照
- 教训：**P1 时 L1 借贷平衡是通过的，缺陷完全没暴露。** 只有加上 L2（快照 vs 流水）这层校验，"账目对但余额错"才会现形。对账分层不是形式主义，每一层抓的是不同类的 bug

### 5.2 压测线程池小于并发数，latch 永久死锁

- 现象：S4-a 跑了 6 分钟无任何进展，数据库侧锁等待 0、无长事务，完全空闲
- 根因：`newFixedThreadPool(64)` 配 `CountDownLatch(500)`。前 64 个任务 countDown 后全部阻塞在 `fire.await()`，剩余 436 个任务在队列里排不到线程，`ready.await()`（无超时）永远等不齐
- 修复：S4-a 去掉对齐释放改为固定线程池持续消化（500 并发本就超过连接池 20，虚构瞬时并发无意义）；S4-b 确实需要瞬时同时到达，则把线程池设为等于并发数，并给所有 `await` 加超时
- 教训：**"对齐瞬时释放"模型要求线程池大小 >= 并发数**，这是 P1 的 `SpikeLoadClient` 用 `newFixedThreadPool(concurrency)` 时隐含满足、换个写法就会踩的坑。另外任何 `latch.await()` 都应该带超时，否则卡住时没有任何诊断信息

### 5.3 查询 id 范围与雪花 ID 重叠，误判压测进展

- 现象：排查 5.2 时查 `WHERE id >= 900000000000` 想看 S4 进展，结果把所有历史任务（雪花 ID 约 1e18）都算进来了，显示一堆 ACCEPTED/LOCKED 干扰判断
- 修复：S4 固定 id 段查询必须写闭区间 `BETWEEN 900000000000 AND 900001000000`
- 教训：造数用固定 id 段是好做法（便于精确清理），但查询时必须写闭区间——开区间会撞上雪花 ID 的量级

## 6 已知边界

- **结算 TPS ≈191 是同机、64 线程、关闭 MQ 的口径**，不是系统上限。开启事务消息后会因半消息 + commit 两次 RPC 而下降，需在 P7 单独测
- 仲裁支持跑腿的分支（DISPUTED→SETTLED）只有领域层与 CAS SQL，application 用例在 P4 补齐
- 取货（ACCEPTED→PICKED_UP）同样缺用例，`SettlementIT` 目前用 SQL 直接改状态绕过，P4 修掉
- 三层对账的 L2 只校验系统户。用户账户初始余额由 seed 直接给、无对应流水，口径上不适用"快照 == 流水净额"，需要改成"增量比对"才能纳入
