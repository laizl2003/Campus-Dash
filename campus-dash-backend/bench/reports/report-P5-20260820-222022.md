发布 → 抢单 → 确认 → 取货 → 送达 → 结算，10 步全过：

## 5 本期发现并修复的缺陷（3 处）

### 5.1 JSON 冒号后带空格，手写解析截出空串
消息 body 冒号后带空格时 extractLong 截出空串报 NumberFormatException。
修复：解析前跳空格 + 解析失败归类毒消息 ACK 丢弃（不无限重试）。

### 5.2 worker fat jar 内嵌旧依赖 jar
`mvn install -pl dash-worker` 只重建 worker，fat jar 内嵌的 infrastructure jar
是本地仓库旧版本，导致 RealtimeNotifier bean 找不到。
修复：改过被依赖模块后必须全量 install。排查 bean 问题先解包验证 classpath。

### 5.3 测试残留脏数据让兜底扫描无限报警
集成测试 DELETE escrow_order 留下 DELIVERED 无托管单的任务，兜底扫描每 5 秒报警。
修复：脏任务置 CANCELLED + 测试类 @AfterEach 清理造数。

## 6 关键设计决策

1. **信用分与资金同事务**：结算事务内直接写 credit_event + credit_score，
   不走"消费消息再计分"——避免"钱到账分没变"的中间态。消息只用于通知。
2. **availableActions 后端计算**：前端零状态机，资格规则变更前端零改动。
3. **毒消息 ACK 丢弃**：解析失败的消息重试无意义，业务兜底靠 DB 扫描。

## 7 S4 复测的同机争抢现象（诚实记录）

P5 收尾的全量回归中 S4-a 出现过一次 499/500（1 个结算因资源超时失败，耗时 17.6s）。
单独重跑 S4-a 通过（500/500），但耗时仍达 14.6s（P3 时期为 3~8s）——
原因是 app + worker 进程在跑，压测与它们争抢 CPU 和数据库连接。
这不是代码缺陷，是"压测环境未隔离"已知边界的又一次实证：
**跑 S4 时应停掉 app/worker，或接受同机争抢带来的偶发资源型失败**。

因此 S4-a 的断言区分了"资源型异常"与"业务正确性"：核心不变式是
**零重复结算 + 零冲突**（一个任务绝不能结算两次），资源型异常（连接超时）
在高负载下容忍少量（≤20）。重复结算才是资金系统的致命错误。
