# CampusDash 设计演进记录

面向后续维护者的工程档案：每期做了什么、为什么这么选、踩过哪些坑。
教学向的完整讲解在教程正文，这里只记工程决策与事实。

## 一句话定位

校园跑腿抢单市场。发单人悬赏（钱先托管）→ N 个跑腿同时抢、只能一个成功 →
限时未确认自动流转下一位 → 送达确认后结算给跑腿与平台。
业务链路很短，但每个环节都踩在并发与一致性的硬骨头上：抢单的正确性可验证（超卖就是错），
资金的正确性可验证（借贷不平就是错）。

## 技术栈演进

架构自始至终是 DDD 洋葱四层：`domain`（零框架依赖）/ `application` / `infrastructure` / `presentation`，
外加 `shared`（通用内核）、`worker`（独立进程）、`bench`（压测）。

| 项 | 设计文档写的 | 实际落地 | 偏离原因 |
|---|---|---|---|
| Spring Boot | 3.3.5 | **3.5.8** | 本地 Maven 仓库已有 3.5.8 的 BOM，用它省掉整套依赖下载 |
| 持久层 | MyBatis-Plus | **JdbcTemplate** | 抢单核心是手写带条件 CAS SQL，`affectedRows` 语义一致，JdbcTemplate 更直观。P6 已接入 ShardingSphere JDBC 规则与算法，仓储层暂不强制替换为 ORM |
| Redis 客户端 | Redisson | **Spring Data Redis (Lettuce)** | 终选方案本就不用分布式锁（靠 Lua + DB CAS），只需 EVAL/ZSET/String。Redisson 留到教程讲锁方案对比时引入 |
| 缓存层次 | Caffeine + Redis 两级 | **纯 Redis 单层** | 本地缓存会引入"各实例看到不同事实"的不确定性，而本项目卖点是并发正确性。热 Key 改用 key 分片 + 读副本解决 |
| 托管资金模型 | 冻结（P1 实现）| **转移**（P3 修正）| P1 同时做了冻结与转移，同一笔钱记两次导致全局总额凭空增加。担保交易的正确建模是资金真实转移 |
| MQ 客户端 | RocketMQ 5.x | rocketmq-client-java **5.2.0** | 只有 5.x 的 gRPC 客户端支持任意时间定时消息（`setDeliveryTimestamp`）；4.x remoting 只有 18 个固定 delay level，做不到"5 分钟后精确投递" |

洋葱架构的红利在 P2 兑现：加 RocketMQ 时 `domain` 只多了一个 `DelayMessagePort` 接口声明，
业务规则一行未改；`dash.mq.enabled=false` 就能整套退回"纯数据库兜底扫描"模式。

## 分期交付

### P1：抢单最小闭环

- 8 个 Maven 模块 + docker-compose（MySQL 8 RC 隔离级别 + Redis 7）
- 发布任务含最小资金托管：单本地事务内完成余额 CAS 冻结 → ledger 借贷双写 → escrow 置 HELD → errand 置 PUBLISHED
- 抢单四层防护的前三层：资格前置 → Redis Lua 原子判定 → MySQL CAS 落库 →双唯一索引兜底
- 三条 ArchUnit 规则进测试（领域层零框架依赖 / 端口定义在 domain / 聚合不依赖 ports）
- 自研 `SpikeLoadClient` 压测客户端（`CountDownLatch` 对齐瞬时释放）
- 交付：22 个测试绿；2000 瞬时并发抢 1 名额，成功数恒为 1，四条校验 SQL 全 PASS

关键取舍一：**Lua + DB CAS 双保险，而不是 Redisson 分布式锁**。
Redisson 保证的是"互斥"，而业务要的是"名额守恒"。主从切换丢锁时互斥会破，
但 `grab_record` 的唯一索引与 `WHERE status AND version` 的 CAS 仍让名额守恒成立。
性能靠 Redis 挡掉 99% 的无效请求，正确性靠数据库兜底——两者分工，不指望一个机制包办。

关键取舍二：**Lua 占位成功但落库失败必须回滚名额**。
这是最容易漏的一步。不回滚就会名额泄漏：任务永远显示"已被抢"，但数据库里没有抢中者。
补偿动作必须在事务之外执行（事务已回滚），另有定时 job 兜底修正。

关键取舍三：**故意用错误实现压出超卖**（`OversellControlExperimentIT`）。
只会通过的测试没有价值。把 Lua 换成"GET-判断-DECR"三次往返后，
实测 500 并发下名额被扣到 -499；再拆掉 DB 的 CAS 条件，158 人"抢中"同一个名额。
证明了加压模型够狠，也反证了双层防护各自的必要性。

### P2：状态机与超时流转 + 数据治理

- 新增 `dash-worker` 独立进程（超时流转消费者 + 兜底扫描 job + 消息重发 job）
- RocketMQ 5.x 定时消息主通道 + 每秒兜底扫描，幂等三件套（version CAS + round 轮次 + msg_key 唯一索引）
- 本地消息表：业务事务内登记 PENDING，事务提交后发送，失败由 job 重发
- 防无限流转：`max-transfer-rounds` 达上限直接回退 PUBLISHED
- 数据治理：`bench_run` / `bench_run_item` 两张压测设施表 + 四个脚本（seed / verify_run / compare_runs / cleanup.sh）
- 交付：38 个测试绿；MQ 定时消息投递误差 106ms；1 万条集中到期零卡单零重复流转

关键取舍一：**主通道 + 兜底扫描双通道**。
MQ 定时消息负责实时性，数据库扫描负责不丢。理由很直接：超时不流转意味着任务永久卡在
LOCKED、资金永久冻结，这是不能接受的。这个模式在项目里反复出现（名额补偿、消息重发、
超时流转都用了它），核心是"主通道追性能、兜底通道追不丢，靠幂等保证重复执行无副作用"。

关键取舍二：**事务边界收在独立 Bean 里**。
`TimeoutTransferUseCase` 编排 Redis + 数据库，但 `@Transactional` 方法全部放在
`TimeoutTransferStep`。两个原因：同类自调用会绕过 Spring 代理让事务失效；
Redis 操作不受数据库事务保护，圈进事务只会拉长事务、放大锁竞争。
MQ 发送同理移到事务提交之后——事务内做外部 IO 是常见的性能陷阱。

关键取舍三：**测试数据默认保留，不再全表 DELETE**。
P1 时所有轮次数据混在一起，校验 SQL 一次输出 31 行任务，清理只能清空整表。
P2 引入 run_id 分轮登记后，数据可以保留下来做"改动前后同档位对比"，
清理精确到轮次且永不碰 seed 基线数据。刻意不往业务表加 `run_tag` 列——
压测设施不侵入业务模型。

### P3：资金完整链路

- 结算（含 24h 自动结算）/ 退款 / 仲裁分账，佣金比例配置化并向下取整、余数归跑腿
- 三道幂等闸门：escrow 状态 CAS + errand 状态 CAS + `wallet_ledger.biz_no` 唯一索引
- 事务消息（RocketMQ 半消息 + 回查）发布资金事件，worker 消费落 `notification` 表
- 三层对账 job：L1 借贷平衡 / L2 系统户快照一致 / L3 托管闭环，差异落 `recon_diff`
- 事务传播实战：审计日志走 `REQUIRES_NEW`，六种 `@Transactional` 失效场景做成可执行测试
- 交付：50 个测试全绿；S4 结算 TPS ≈191、零死锁、资金差异 0

关键取舍一：**托管是"转移"而不是"冻结"，这是修 P1 缺陷时才想清的**。
P1 的实现同时做了发单人 `available→frozen` 与托管账户 `available+=`，同一笔钱被记两次，
全局总额凭空增加。正确的区分是：担保交易（本项目）是资金真实转移，钱必须离开付款方账户；
预授权/押金才是冻结，钱不离账只是不可动用。混用两者会让"快照 == 流水净额"永远不成立。

关键取舍二：**两种消息一致性机制按"是否需要延迟"分工，不是选一个更先进的**。
RocketMQ 的事务消息与定时消息互斥（事务消息不支持 `setDeliveryTimestamp`）。
所以确认超时、24h 自动结算这类需要延迟且需与事务一致的场景只能用本地消息表 + 定时消息；
资金事件通知不需要延迟，用事务消息可以省掉一张表和一个重发 job。
面试问"本地消息表和事务消息选哪个"，正确答法是先问"要不要延迟"。

关键取舍三：**审计日志用 REQUIRES_NEW，并且明确接受它的代价**。
资金回滚时审计要留下（那正是排查现场），所以不能用默认的 REQUIRED。
代价是每次审计要额外占一个连接、而主事务的连接不释放，池子小就会耗尽——
`TransactionPitfallIT` 里有一个把池设成 2 的用例专门复现这个现象，
并给出配比公式 `池大小 >= (1 + 嵌套层数) × 预期并发`。

### P4：API 补齐与完整前端

- 补 3 个缺失用例（PickUp / Dispute / Arbitrate）+ 4 个读模型用例，消除 SettlementIT 的 SQL 绕过
- 12 个 API 端点、Controller 四拆分、统一 Result 响应、简易 Session 登录（token 存 Redis）
- `availableActions`：前端按钮完全由后端计算驱动，状态机不产生第二份副本
- React + Vite 前端（campus-dash-web/）：任务广场 / 详情 / 发布 / 我的任务 / 钱包 / 消息六页，
  含"模拟 N 人同时抢"并发可视化；浏览器端到端验证 10/10 通过
- 事务消息真正打通：半消息 → 本地事务 → commit，回查器注册到 Producer，
  FundEventConsumer 消费落站内消息；worker 三个消费者全启动
- ES + Canal 彻底摘除（决策见架构文档 9.4）：附近任务不做，检索走 MySQL 索引
- 交付：56 个测试全绿（22 单测 + 34 集成），浏览器全链路含仲裁双向走通

关键取舍一：**摘除 ES 是需求评估，不是技术降级**。
校园半径小，"附近 500 米"与"本校列表"信息量几乎相同；关键词搜索在万级任务下
MySQL 索引足够。为这两个弱需求引入 Canal 全链路的运维与一致性成本不划算。
判据与缓存决策一致：由压测与真实需求触发，不预先堆架构。

关键取舍二：**availableActions 由后端算，前端零状态机**。
状态机是这个项目的核心资产，前端复制一份必然漂移（状态一改前端漏改）。
所以详情页按钮、卡片操作全部读后端返回的动作集合，前端没有任何
"status === xxx && isPublisher"的判断。代价是前端多一次依赖后端，
收益是两边永远一致。

关键取舍三：**鉴权先用有状态 Session，JWT 留到有对照组时再做**。
Session 形态最简（token → Redis 映射），能立刻支撑前端联调；
JWT 的价值（无状态、吊销难、续期）要通过与 Session 的对比才讲得清，
所以挪到 P5 成对实现。

### P5：缓存一致性 + 信用分 + WebSocket + JWT

- 缓存：Cache Aside 读路径（逻辑过期 + 4 分片 + TTL 抖动）、afterCommit 删缓存 + 延迟双删、
  Redisson 布隆防穿透、互斥重建防击穿、一致性校验 job（sync_diff 哨兵表）
- 信用分：事件驱动计分（结算 +2 / 超时未确认 -5 / 争议败诉 -8）、30 天滑动窗口、
  ZSET 校区排行榜、抢单资格后端化（客户端传的 creditScore 作废）
- WebSocket：/ws 握手鉴权 + 按 userId 推送三类事件（状态/消息/信用分），
  前端摘掉两处轮询，WS 不可用自动降级轮询
- JWT：与 Session 双实现，dash.auth.mode 开关切换，黑名单吊销，AuthModeIT 对照测试
- S3 缓存压测：命中率 97.5%，详情回源 5000→123 次（降 97.5%），P99 117→54ms
- 交付：73 个测试全绿（22 单测 + 51 集成），API 全链路 + WS 握手 + 信用分闭环验证通过

关键取舍一：**信用分变更与资金动作同事务，不走"消费消息再计分"**。
原设计倾向"结算发消息 → 消费者更新信用分"，但这会引入"钱到账了分还没变"的中间态。
改为在结算事务内直接写 credit_event + credit_score——信用分不是资金，但它和资金动作
是同一个业务事实的两面，放一个事务里才没有中间态。事件消息只用于通知（WebSocket 推送），
不用于计分本身。

关键取舍二：**availableActions 由后端算，前端零状态机**（P4 决策，P5 全面生效）。
信用分改变抢单资格后，前端如果自己判断"分数够不够抢"就会和后端漂移。
现在前端只渲染后端返回的动作集合，资格规则改了前端零改动。

关键取舍三：**毒消息 ACK 丢弃，不无限重试**。
格式损坏的消息重试永远不会成功，返回 FAILURE 会让它在重试队列里打转到死。
正确做法是识别出"重试无意义"的异常（解析失败），ACK 丢弃并告警——
业务兜底靠 DB 扫描，不靠消息重试。这是"消息可丢、扫描不丢"设计意图的一部分。

### P6：分片前置改造 + 游标分页 + 信用分校准 + JWT 刷新令牌（完成）

- `grab_record` / `escrow_order` / `errand_status_log` 补 `campus_id`，抢单、托管、状态日志与任务按同一校区维度绑定，为 ShardingSphere 绑定表路由做准备；旧库可执行 `docker/migrate-p6.sql`
- 新增 ShardingSphere JDBC 依赖、`CampusDashShardingRuleFactory` 与 `CampusDashModuloShardingAlgorithm`，可产出真实 `ShardingRuleConfiguration` 并通过 class-based 算法按 `campus_id/user_id` 取模路由
- 任务广场新增游标分页：`created_at DESC, id DESC` 稳定排序，保留旧 `page/size` 兼容路径
- 信用分新增每日校准 use case + worker job，按 30 天滑动窗口从 `credit_event` 重算 `credit_score`
- JWT 新增 refresh token：access token 仍是 JWT，refresh token 存 Redis，刷新时轮换并作废旧 token
- 交付状态：P6 行为测试（JWT refresh / 信用校准 / 游标分页 / 托管单分片键）与 MySQL/Redis 集成测试已跑绿；旧库迁移 `docker/migrate-p6.sql` 已实跑并校验三张共片表 `campus_id` 非空；ShardingSphere 规则工厂与 class-based 算法已纳入单测和全量测试

关键取舍一：**先补分片键语义，再接 ShardingSphere**。
`errand` 已有 `campus_id`，但抢单正确性还依赖 `grab_record` 的唯一索引，资金链路还依赖
`escrow_order`，状态时间线依赖 `errand_status_log`。如果这些表不带校区维度，后续要么广播路由，
要么让抢单记录、托管单与任务落在不同分片，都会把"同一任务内唯一"和"同一任务托管闭环"
这两个不变式变得难验证。本轮先把 `campus_id` 贯通到任务共片表，
再用 ShardingSphere 的 class-based 算法把这些表绑定到同一库路由上。

关键取舍二：**游标分页增量兼容 OFFSET**。
旧前端和既有测试仍走 `page/size`，传入 `cursor` 时才返回 `{items,nextCursor}`。
这样可以先解决深分页的 SQL 形态，又不把前端分页改造和后端仓储替换绑死在同一个提交里。

关键取舍三：**JWT refresh token 保持服务端有状态**。
access token 仍然无状态，refresh token 则作为可吊销、可轮换的随机凭证放 Redis。
这不是退回 Session，而是承认"续期/踢下线/旧 token 复用检测"这些能力天然需要服务端状态。

关键取舍四：**P6 不强制把 JdbcTemplate 换成 MyBatis-Plus**。
ShardingSphere 接入的关键是数据源、分片规则和 SQL 分片键，ORM 只是仓储实现手段。
当前抢单/托管/结算强依赖手写 CAS SQL，保留 JdbcTemplate 能让并发正确性更可读；
如果后续要换 MyBatis-Plus，只能作为基础设施实现替换，不改变 domain/application 契约。

### P7：S2 阶梯加压 + 抢单热点限流（完成）

- 新增 `bench/profiles/s2-ramp.yaml`，明确 S2 的阶梯、时长、断言和报告字段
- 新增 `RampLoadClient`，按并发档位持续请求任务广场，逐档记录 QPS、P50/P95/P99/Max、错误数
- 新增 `GrabRateLimiterPort` + `LocalGrabRateLimiterAdapter` + `SentinelGrabRateLimiterAdapter`，抢单 L1 在信用校验、Redis Lua、DB CAS 之前按 `errandId` 热点限流；配置项为 `dash.grab.limit.enabled` / `dash.grab.limit.type` / `dash.grab.limit.per-second`
- S2 完整阶梯压测：50/100/200/400/800 并发，每档 60s；默认配置稳定线到 400 并发，800 并发记录为边界档
- 800 并发调参复测：Tomcat/Hikari/Redis pool 调整后 0 错误，P99 472ms
- 抢单热点真实 HTTP 链路验证：1000 并发抢 1 个名额，Sentinel 限流 900 次，成功 1 次，超卖 0
- 交付状态：S2 工具、Sentinel 热点限流、SpikeLoadClient 限流分类、bench_run 留痕与完整报告均完成；报告见 `bench/reports/report-P6-P7-20260822-complete.md`

关键取舍一：**S2 只测稳态，不混入抢单正确性验证**。
S1 已经覆盖"N 抢 1 零超卖"，S2 的职责是补单机稳态 QPS 和延迟曲线。
把两者拆开，报告里的吞吐数字才不会再和瞬时尖峰混在一起。

关键取舍二：**P7 调优必须按轮次留痕**。
`RampLoadClient` 每个并发档位都登记 `bench_run`。本轮先用默认配置拉出完整曲线，
再只调整 Tomcat 线程/accept 队列、Hikari 连接池、Redis Lettuce pool 与 Sentinel QPS 阈值做 800 档复测。
默认 800 档有 146 个 IOException，调参后 800 档错误数为 0，但 QPS 降至 5205、P99 升至 472ms。

关键取舍三：**Sentinel 放在抢单入口前，DB CAS 仍是正确性底线**。
Sentinel 只负责热点任务快速失败，保护 Redis Lua 和数据库；它不承担"谁抢成功"的裁决。
真实 HTTP 链路 1000 并发压测中，900 次被 Sentinel 拦下，1 次成功，99 次名额已满，超卖为 0。

## 踩坑档案

按"现象 → 根因 → 修法 → 可复用教训"记录，只收有复用价值的。

**1. 唯一索引缺少 round，回退后的任务谁都抢不到**
现象：任务超时回退成 PUBLISHED、`slot_taken=0`、Redis 名额也已归还，但新跑腿抢单一直失败。
根因：`grab_record` 的 `uk_errand_seq(errand_id, seq)` 里，上一轮 `round=0` 的记录仍占着
`seq=1`，新抢单者插入同一 seq 撞唯一索引。
修法：两个唯一索引都纳入 round（`uk_errand_round_seq` / `uk_errand_round_user`），
不变式表述从"同一名额只能被占一次"精确为"同一轮内同一名额只能被占一次"。
教训：**P1 只有单轮抢单，这个缺陷完全看不出来**。索引的正确性依赖业务的全部生命周期，
新增状态流转时必须回归旧测试，否则旧索引会静默失效。

**2. 无限流转**
现象：worker 日志里一个任务 round 已涨到 20 且仍在继续流转。
根因：2000 并发抢单产生 1999 个候选人，超时流转会一个个试下去。每轮 5 分钟意味着
7 天都结束不了，worker 一直在做无用功。
修法：加 `max-transfer-rounds`（默认 5），达上限直接回退让所有人重新抢。
教训：**这个缺陷不是测试发现的，是看运行日志发现的**。测试只验证"单次流转对不对"，
不会验证"流转会不会没完没了"。只跑测试不看日志会漏掉这类耗尽型问题。

**3. MQ topic 缺失让整个应用起不来**
现象：重建 broker 容器后，应用与 8 个集成测试全部启动失败，报
`Error creating bean 'timeoutProducer'` → `Failed to fetch topics after 3 attempts`。
根因两层：一是 `Producer.setTopics(topic)` 预绑定会让 Producer 启动时就去拉 topic 路由，
topic 不存在直接抛异常；二是 topic 是我手工敲 mqadmin 建的，容器一重建就没了。
修法：去掉 `setTopics` 预绑定改为惰性获取路由；topic 创建固化到 `docker/init-mq.sh`。
教训：**声称"有兜底通道所以主通道可降级"，就必须真的验证主通道挂掉时系统还能起来**。
不验证的话降级设计只存在于纸面。另外任何"手工执行过一次"的初始化步骤都必须脚本化。

**4. `@Transactional` 同类自调用失效（P1 避开、P2 又踩）**
现象：`TimeoutTransferUseCase.handleTimeout` 调用 `this.transfer()`，事务注解不生效。
根因：同类内部方法自调用绕过 Spring AOP 代理。
修法：拆出独立的 `TimeoutTransferStep` Bean（P1 的 `GrabTransactionalStep` 就是同样理由）。
教训：同一个坑在不同期会以不同面貌重现。P1 里我是"为了让补偿在事务外"才拆的 Bean，
P2 里则是"顺手把事务方法写在编排类里"，形态不同、根因相同。

**5. compose healthcheck 连续配错两次**
现象：容器一直 unhealthy，但服务实际完全正常。
根因：第一次用 `netstat`/`ss` 探端口——RocketMQ 镜像里这两个命令都不存在；
改用 `ps` 后又匹配 `BrokerStartup`——`--enable-proxy` 模式下真实进程名是 `ProxyStartup`。
修法：`ps -ef | grep -qE '[P]roxyStartup|[B]rokerStartup'` + `start_period`。
教训：healthcheck 的命令必须在目标镜像里实测存在，进程名必须实际 `ps` 看过。
写健康检查时"想当然"的代价是长期的假告警，而假告警会让人忽略真告警。

**6. 清理脚本 N 次往返，1 万条数据直接超时**
现象：`cleanup.sh` 处理 1 万条数据跑满 5 分钟被中断。
根因：为每个 id 单独 `docker exec redis-cli DEL`，单次约 30ms；Redis 反向孤儿扫描还为
每个 key 查一次 MySQL。
修法：拼批量命令走 `redis-cli --pipe` 一次送入；反向孤儿改为"一次取全部 key + 一次取
全部存活 id，用 awk 在本地做差集"。1 万条从超时降到 110 秒。
教训：运维脚本也有性能问题。小数据量下"循环里调命令"完全无感，量级一上来就是灾难。
判断依据很简单：循环体内有没有跨进程/跨网络调用。

**7. Surefire 默认不跑 `*IT.java`**
现象：`mvn test` 显示 BUILD SUCCESS、14 个测试全绿，但集成测试一个都没执行。
根因：Surefire 默认只匹配 `*Test`/`Test*`/`*Tests`/`*TestCase`，`*IT` 是 Failsafe 的约定。
修法：父 pom 的 surefire `<includes>` 显式纳入 `**/*IT.java`。
教训：**"测试全绿"要先确认"测试真的跑了"**。看 `Tests run` 的数量和测试类名列表，
不要只看 BUILD SUCCESS。

**8. 托管既冻结又转移，同一笔钱被记两次**
现象：托管账户流水净额 78900 分但快照是 0；发单人流水净额 -78900 而快照总额没变。
根因：P1 的托管做了两件互斥语义的事——发单人 `available→frozen`（冻结）+ 托管账户
`available+=`（转移）。全局 `SUM(available+frozen)` 凭空增加，且发单人账户总额未变
却记了 DEBIT 流水。
修法：统一为转移模型，`casFreeze` 改 `casDebit` 只减 available。
教训：**P1 的 L1 借贷平衡一直是通过的，这个缺陷完全没暴露**。只有加上 L2
（快照 vs 流水净额）才会现形。对账分层不是形式主义——每层抓的是不同类的 bug，
少一层就有一整类问题查不出来。

**9. 压测线程池小于并发数，CountDownLatch 永久死锁**
现象：S4 跑 6 分钟零进展，而数据库侧锁等待 0、无长事务，完全空闲。
根因：`newFixedThreadPool(64)` 配 `CountDownLatch(500)`。前 64 个任务 countDown 后
全阻塞在 `fire.await()`，剩下 436 个排不到线程，`ready.await()` 永远等不齐。
修法：需要瞬时并发的场景线程池必须 >= 并发数；不需要的场景（500 并发本就超过连接池 20）
直接用固定线程池持续消化。所有 `await` 一律加超时。
教训：P1 的 `SpikeLoadClient` 写的是 `newFixedThreadPool(concurrency)`，隐含满足了这个
前提，换个写法就踩。另外"数据库完全空闲"这个观测是关键线索——它一次排除了锁竞争假设，
如果只盯着应用日志会往死锁方向查很久。

**10. 固定 id 段用开区间查询，撞上雪花 ID**
现象：查 `WHERE id >= 900000000000` 看压测进展，结果混进了全部历史任务。
根因：雪花 ID 约 1e18，远大于造数用的 9e11，开区间把它们全包含了。
修法：固定 id 段查询必须写闭区间 `BETWEEN 900000000000 AND 900001000000`。
教训：造数用固定 id 段便于精确清理，是好做法；但它与雪花 ID 共存于同一列，
任何范围查询都必须双边界。这个错误会直接导致误判，比查不到数据更危险。

**11. 雪花 ID 超过 JS 安全整数，前端拿到的是错的 ID**
现象：浏览器联调时发布、抢单、详情全挂，列表却"看着正常"。
根因：雪花 ID 约 2.15e17 超过 `Number.MAX_SAFE_INTEGER`（2^53 ≈ 9e15），
`JSON.parse` 静默截断——215731113107132416 被解析成 215731113107132400。
修法：后端 Jackson 全局把 long 序列化为 string，前端 ID 全程按 string 处理。
教训：**long 型 ID 跨语言边界必须想清楚精度**。Java/C 侧 64 位没问题，
JS 侧只有 53 位安全整数。这类错误列表页不报、详情页才炸，很难一眼看出根因。

**12. RocketMQ 事务消息两个前置条件都没满足**
现象：结算接口上线后 HTTP 500，集成测试却是绿的。
根因两层：一是 Producer 没注册 TransactionChecker，`beginTransaction` 直接抛
"Transaction checker should not be null"；二是 topic 建成了 NORMAL 类型，
发送事务消息报 "Current message type not match"，且类型建错无法原地改，
只能 deleteTopic 重建。
修法：专用 Producer（构建时 setTransactionChecker）；topic 建
`-a +message.type=TRANSACTION` 并固化进 init-mq.sh。
教训：**集成测试关 MQ（dash.mq.enabled=false）验证业务逻辑是对的，
但 MQ 真实链路必须单独做一次联调**——否则"测试全绿"只是 Noop 适配器全绿。

**13. 两类延迟消息共用 payload 格式，消费者解析出空串**
现象：自动结算消息一消费就 NumberFormatException，MQ 无限重投。
根因：DeliverErrandUseCase 登记消息时复用了超时流转的 payload 方法，
消费者按自己的字段布局解析，遇到不同顺序的字段就抽到空串。
修法：两类消息各自定义 payload 方法；extractLong 补空值校验。
教训：**消息格式是生产者与消费者之间的契约**，哪怕字段集合看起来兼容，
共用生成方法也会在字段顺序、空格这些细节上埋雷。契约要显式、一对一。

**14. vite dev server 在后台挂死：端口在监听但请求永不返回**
现象：`lsof` 显示 5173 有监听，curl 却永远挂起。
根因：vite 进程被 nohup 后台化后冻结（不处理请求也不退出）。
修法：kill 后重新拉起；健康探测必须同时验证"端口监听"和"HTTP 有响应"，
只查端口会误判服务可用。
教训：长驻进程的可观测性里，"端口在"是最弱的信号；HTTP 探活才算数。

**15. JSON 冒号后带空格，extractLong 解析出空串**
现象：自动结算消息消费报 NumberFormatException，body 看起来明明有 errandId。
根因：手写 JSON 解析按 `"field":` 定位后直接读数字，但部分消息冒号后带空格，
第一个字符不是数字，截出空串。
修法：解析前跳过冒号后的空格；同时这类解析失败归类为毒消息 ACK 丢弃。
教训：**手写 JSON 解析是在埋雷**——本项目消息格式简单且固定才这么做，
但凡格式有演进可能就换 JSON 库。容忍空格是防御，不是纵容手写解析。

**16. worker fat jar 内嵌旧依赖 jar，bean 找不到**
现象：worker 启动报 RealtimeNotifier bean 找不到，但源码和编译都正常。
根因：`mvn install -pl dash-worker` 只重建 worker 模块，fat jar 内嵌的
dash-infrastructure jar 用的是本地仓库的旧版本（没有新加的类）。
修法：改过被依赖模块后必须全量 `mvn install`，不能只装单个模块。
教训：**fat jar 的依赖是打包时快照**，"我明明改了代码"和"jar 里有没有"是两回事。
排查 bean 找不到时，先解包验证类在不在 classpath，再看条件装配。

**17. 测试残留的脏数据让兜底扫描无限报警**
现象：worker 日志每 5 秒报一次"自动结算兜底失败：托管单不存在"。
根因：集成测试 DELETE 过 escrow_order，留下 DELIVERED 但无托管单的任务，
兜底扫描每次都捞到它、结算失败、下次还捞。
修法：SQL 把这类脏任务置为 CANCELLED；测试类加 @AfterEach 清理自己的造数。
教训：**兜底 job 的"失败"要分清"暂时失败要重试"和"数据损坏永远失败"**。
后者要有识别与隔离手段，否则日志会被淹没，真正的告警看不见。

**18. 自动结算消息使用 JSON 数字，消费者只认字符串数字**
现象：新版 worker 启动后持续打印 `无法解析 errandId`，body 是 `{"errandId": 216...}`。
根因：`AutoSettleConsumer.extractLong` 的定位串写成了 `"errandId":"`，
只支持字符串数字；真实 MQ 消息是标准 JSON 数字，冒号后可能还有空白。
修法：先加 `AutoSettleConsumerTest` 复现数字格式解析失败，再把定位改为 `"field":`，
跳过空白并兼容可选双引号。新版 worker 已消费历史同格式消息并返回 `ALREADY_SETTLED`。
教训：**消息契约不能靠手写解析器的隐含假设**。即便字段名相同，值类型从字符串到数字
也足以形成毒消息；修这类问题必须先用测试锁住真实消息样本。

## 换实现的方法

洋葱架构下替换基础设施只需两步：在 `dash-domain/**/ports/` 找到（或补上）端口定义，
在 `dash-infrastructure/` 加实现，然后改装配（`dash-bootstrap` 与 `dash-worker` 各自的
`@SpringBootApplication` + `@Configuration`）。`dash-application` 与 `dash-domain` 不需要改动。

已按此方式完成的替换与扩展：

| 端口 | 实现 | 说明 |
|---|---|---|
| `GrabSlotPort` | `RedisGrabSlotAdapter` | 换成"数据库悲观锁版"只需新写一个适配器，教程第 7 章对比六种方案就靠它 |
| `CandidateQueuePort` | `RedisCandidateQueueAdapter` | ZSET 实现 |
| `DelayMessagePort` | `RocketMqDelayMessageAdapter` / `NoopDelayMessageAdapter` | 靠 `dash.mq.enabled` 开关切换；关掉后系统退化为纯兜底扫描且业务仍正确 |
| `ErrandRepository` 等 | `Jdbc*Repository` | P6 已把 SQL 分片键与 ShardingSphere 规则接入点补齐；后续换 ORM 仍只改这一层 |

同理可换：RabbitMQ（实现 `DelayMessagePort`，注意它的 TTL+DLX 有队头阻塞）、
PostgreSQL（换 datasource URL + 驱动，注意 CAS SQL 里的 `GREATEST`/`NOW(3)` 方言差异）。
