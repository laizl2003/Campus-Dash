# 注册、验证码与账号表

## 1. 为什么先做这一层

需求里"注册接口"只是表面，真正的分水岭是**用户主键的类型**：

- 现在全系统（钱包 owner、任务 publisher/grabber、流水 user_id、信用分、MQ 资金事件、JWT 主体）都是 `long`；
- 新需求要求 `user_id` 是 UUID 字符串，仲裁账号还是 `001`。

所以这一步先把**账号本身**落地（表、验证码、注册），登录与身份切换单独做，
避免一次性改动 130 处 `long` 声明把系统改坏。

## 2. 表结构

```sql
CREATE TABLE IF NOT EXISTS `user` (
  user_id             VARCHAR(36)  NOT NULL COMMENT '注册用户是 UUID，Admin 固定 001',
  username            VARCHAR(32)  NOT NULL,
  phone               VARCHAR(20)  NOT NULL,
  password_hash       VARCHAR(160) NOT NULL,
  password_updated_at DATETIME(3)  NULL,
  created_at          DATETIME(3)  NOT NULL,
  updated_at          DATETIME(3)  NOT NULL,
  role                VARCHAR(16)  NOT NULL DEFAULT 'user',
  avatar_url          VARCHAR(255) NOT NULL DEFAULT '',
  campus_id           BIGINT       NOT NULL DEFAULT 1,
  credit_score        INT          NOT NULL DEFAULT 60,
  status              TINYINT      NOT NULL DEFAULT 1,
  last_login_at       DATETIME(3)  NULL,
  last_login_ip       VARCHAR(64)  NOT NULL DEFAULT '',
  login_fail_count    INT          NOT NULL DEFAULT 0,
  remark              VARCHAR(255) NOT NULL DEFAULT '',
  PRIMARY KEY (user_id),
  UNIQUE KEY uk_user_username (username),
  UNIQUE KEY uk_user_phone (phone)
);
```

**冗余字段及理由**

| 字段 | 为什么冗余 |
| --- | --- |
| `credit_score` | 登录返回、列表页都要显示信用分，冗余后免一次回表；校准 job 负责对齐 |
| `last_login_at` / `last_login_ip` | 安全审计与"异常登录"提示，写路径只在登录成功时更新一次 |
| `login_fail_count` | 连续失败计数，后续可加锁定策略；成功登录清零 |
| `status` | 封禁/停用比物理删除安全，登录时校验 |
| `campus_id` | 预留分片键，和 errand/escrow 的 campus_id 对齐 |
| `avatar_url` | 空串表示未设置，前端用用户名首字母占位，不依赖外部图床 |

**唯一性**：`uk_user_username` / `uk_user_phone` 是最终防线。
`existsByUsername` 只是为了给友好错误码，两个请求同时通过检查时靠数据库拒掉一个。

## 3. 验证码

```
GET /api/auth/captcha
→ { captchaId, image: "data:image/png;base64,...", expireSeconds: 300 }
```

- 答案只写 Redis：`auth:captcha:{captchaId}`，TTL 5 分钟；
- 响应里**没有答案**，前端只拿到 id 和图片；
- 校验用 `GETDEL`（原子取用），一次性，重放第二次必然失败；
- 字符集去掉 `0/O/1/I` 等易混字符，大小写不敏感比较。

## 4. 注册

```
POST /api/auth/register
{
  "username": "student_zhang",
  "phone": "13812345678",
  "password": "abc12345",
  "confirmPassword": "abc12345",
  "captchaId": "…",
  "captchaCode": "AB12"
}
→ { "userId": "<uuid>", "username": "...", "phone": "...", "role": "user" }
```

**校验顺序**（先便宜后昂贵，且不泄露信息）：

1. 验证码（一次性，先消耗，挡机器注册）
2. 用户名 `^[A-Za-z0-9_]{3,20}$`
3. 手机号 `^1[3-9]\d{9}$`
4. 密码 8-32 位且同时含字母和数字
5. 两次密码一致
6. 用户名 / 手机号唯一（查库）

> 第 6 步放最后：先查库再校验格式，会让攻击者用注册接口探测"哪些用户名已存在"。

**错误码**

| code | 场景 |
| --- | --- |
| `CAPTCHA_INVALID` | 验证码错误、过期、已被使用 |
| `INVALID_USERNAME` | 长度或字符不合法 |
| `INVALID_PHONE` | 不是 11 位大陆手机号 |
| `INVALID_PASSWORD` | 长度不足或不含字母+数字 |
| `PASSWORD_MISMATCH` | 两次输入不一致 |
| `USERNAME_TAKEN` / `PHONE_TAKEN` | 已存在 |

## 5. 密码存储

格式：`pbkdf2-sha256$迭代次数$盐(base64)$哈希(base64)`

- PBKDF2-HMAC-SHA256，12 万次迭代，16 字节随机盐，256 位输出；
- 比较用 `MessageDigest.isEqual`（常量时间）；
- 迭代次数写在串里，将来调高参数不影响老密码校验。

## 6. 系统仲裁账号

启动时由 `AdminAccountInitializer` 种入（已存在则跳过）：

| 字段 | 值 |
| --- | --- |
| user_id | `001` |
| username | `Admin` |
| password | `12345678` |
| role | `Admin` |

密码是需求固定的，不满足注册接口的复杂度规则，所以它不经过注册流程，直接以哈希入库。
