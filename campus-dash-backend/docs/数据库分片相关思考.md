# Q：为什么要往相关表补 campus_id


不是所有表都补 `campus_id`。下面先回答"为什么必须加"，再给加与不加的清单。

## 为什么要往相关表补 campus_id

`errand` 按 `campus_id` 分片后，ShardingSphere 的世界有一条铁律：**SQL 里没有分片键，它就不知道该路由到哪个分片，只能广播所有分片**。这条铁律会击中现有 schema 的四个地方：

### 1. 查询路由：按 errand_id 反查的语句全部退化为全分片广播

看 [grab_record](file:///Users/haojunpan/Desktop/工作项目/project/ai/ai-agents-from-zero/项目实战-校园跑腿抢单市场/实战项目-线上版本/项目工程/campus-dash/docker/init.sql#L42-L59)：现在所有查询都是 `WHERE errand_id = ?`。errand_id 是雪花 ID，不含校区信息，ShardingSphere 拿到这条 SQL 只能发给**每一个分片**。补上 `campus_id` 并把它设为 grab_record 的分片键后，`WHERE campus_id = ? AND errand_id = ?` 才能精确路由到单分片。

### 2. 绑定表 join：不共片则 join 必跨片

抢单链路有高频 join（任务 ⋈ 抢单记录、任务 ⋈ 托管单）。ShardingSphere 的 binding table 机制要求**两张表用同一个分片键**，join 才能下推到单个分片内完成；否则它要把两个分片的数据都拉到内存里做归并 join——等于把数据库的活搬到应用层干。

### 3. 唯一约束：不共片则全局唯一性被打破

这是最容易被忽略、也最致命的一条。grab_record 的两道防线：

```sql
UNIQUE KEY uk_errand_round_seq  (errand_id, round, seq)      -- INV-1 防超卖
UNIQUE KEY uk_errand_round_user (errand_id, round, runner_id) -- INV-2 防刷单
```

MySQL 的唯一索引**只在单表（单分片）内生效**。如果 grab_record 和 errand 不在同一个分片组，同一个 errand_id 理论上可能出现在两个分片，INV-1 直接失效——这恰好击穿的是本项目"零超卖"的核心卖点。只有 grab_record 按 `campus_id` 与 errand 共片，"同一个任务必然在同一个分片"，唯一约束才继续全局有效。

### 4. 事务收敛：共片才能用单分片本地事务

抢单事务要同时写 `errand`（CAS 占名额）+ `grab_record`（插记录）+ `errand_status_log`。三张表共片 → 还是普通本地事务；不共片 → 要上 ShardingSphere 的 XA/FlexiTransaction，复杂度和故障面完全不是一个量级。

## 补与不补的边界

| 表 | 处理 | 理由 |
|---|---|---|
| `grab_record` | **补 campus_id，与 errand 共片** | 上面四条全中 |
| `escrow_order` | **补 campus_id，共片** | 按 errand_id 查、结算链路高频 |
| `errand_status_log` | **补 campus_id，共片** | 与状态流转同事务写入 |
| `wallet_account` / `wallet_ledger` | **不补，维持 user_id 分片** | 架构文档 10.3 已定：查询都是"我的余额/我的流水" |
| `credit_score` / `credit_event` | **不补，user_id 维度** | 信用是人的维度不是校区维度；排行榜本来就在 Redis ZSET |
| `notification` | 不补 | 按 user_id 查"我的消息" |

## 关于"小幅触碰 domain/application 端口"

接受，而且实际触碰比想象的小。原因：**校园跑腿的请求天然自带校区上下文**——用户永远在某个校区的广场里操作，读路径的 `campus_id` 已经在手；真正要改的主要是两类：

1. **按 errand_id 反查的 repository 端口签名**（如 `GrabRecordRepository.findByErrand(errandId)` 要加 `campusId` 参数）——改的是端口签名，领域规则一行不动
2. **worker 的全局扫描**（`TimeoutScanJob` 按 status 扫全表）——这类没有校区上下文的 job 就让它广播所有分片，低频任务，可接受

这正是洋葱架构 P2 就埋好的伏笔：换存储只改 `infrastructure` 的适配器 + 端口签名，`domain` 的抢单规则、状态机、资金规则零改动。

## 一个要提前认账的遗留问题

补完 `campus_id` 也只解决了**任务维度**的共片。结算链路天然是跨维度的：`errand`（campus 片）+ `wallet_ledger`（user 片），这个跨片事务补什么列都消不掉。对策是承认它、不硬解：校园量级下 `wallet_account` 就两张系统户热点行，可设为广播表或单分片，结算事务仍收敛为"用户分片 + 广播表"的准本地事务；真到需要拆的规模再谈。这一条建议写进 P6 方案的"已知边界"里，面试被追问时主动讲出来，比被问出来强。


# 为什么要基于campus分片？
问的是分片键的选型逻辑——为什么是 `campus_id`，而不是看起来更"标准"的 `errand_id` 或 `publisher_id`。核心一句话：**分片键的选择本质是"优先伺候哪类查询"，而这个项目 90% 的流量是"按校区看任务"**。

## 先看这张表的真实查询画像

`errand` 表上的所有 SQL，按频率排：

| 查询 | 频率 | 条件 |
|---|---|---|
| 广场列表：某校区所有 PUBLISHED 任务 | **最高频**（所有用户反复刷） | `campus_id + status` |
| 任务详情：按 id 查单个任务 | 高频 | `id`（请求自带校区上下文，可补 campus_id） |
| 抢单 CAS：按 id 单行 UPDATE | 高频写 | `id + version` |
| 我的发布/我的接单 | 低频 | `publisher_id` / `grabber_id` |
| 超时扫描（worker job） | 极低频 | `status + locked_at` |

注意一个关键事实：**读流量被"广场列表"统治，而它天然带校区条件**——学生只会刷自己校区的广场，跨校区看任务在这个业务里不存在。写流量全是单行操作（CAS、状态流转），单行操作在任何分片方案下都是路由到一片，不受分片键影响。

## 用排除法看三个候选

**候选 1：按 `errand_id` 哈希分片**（教科书默认答案）

- 写很均匀 ✅
- 但广场列表 `WHERE campus_id = 1 AND status = 'PUBLISHED'` 里**没有分片键**，ShardingSphere 只能广播所有分片、每片查一遍再内存归并排序 ❌
- 等于把最高频的查询打成了最慢的查询。分片是为了扛量，结果把主流量打残，本末倒置

**候选 2：按 `publisher_id` 分片**

- "我发布的任务"快了，但这是低频页
- 广场列表照样跨全部发单人分片广播 ❌，比候选 1 还差

**候选 3：按 `campus_id` 分片**（终选）

- 广场列表：精确路由单分片 ✅
- 详情/抢单：请求上下文本来就有校区，路由无压力 ✅
- "我的任务"：跨片查，但低频，可接受 ⚠️
- 全局统计：跨片聚合，走离线 job 不走在线查询 ⚠️

## 还有两个只有 campus_id 才成立的理由

**1. 业务隔离边界和分片边界重合，跨片需求天然为零。**
东校区的学生不会抢西校区的单，任务、抢单、托管整条链路都封闭在一个校区内。分片最痛的是"业务非要跨片"，而这个业务在领域模型层面就是按校区隔离的——分片键顺着业务隔离线切，一刀下去没有任何跨片缝合成本。这是选分片键的黄金条件：**数据天然按这个维度老死不相往来**。

**2. 上一轮说的共片绑定，只有 campus_id 能当公共钥匙。**
`grab_record`、`escrow_order`、`errand_status_log` 必须和 `errand` 共片（唯一约束防超卖、join 不跨片、事务收敛单分片）。能把"任务 + 抢单记录 + 托管单"这一整条链路串在同一个分片里的维度，只有校区——errand_id 串得起来但列表查询会崩，user_id 根本串不起来（发单人和跑腿是两个人）。

## 代价也要认账

campus 分片有两个已知代价，架构文档 10.3 都写了：

1. **平台级全局统计**（全校区总单量、总流水）要跨片聚合 → 不走在线查询，走离线 job
2. **单校区热点**：如果某个校区量级碾压其他校区，会出现大分片 → 当前规模不用管，真到了那一天再做 `campus_id + hash` 二级拆分，分片键前缀不变，方案兼容

所以面试被问"为什么按 campus_id 分片"，答题骨架就是三步：**查询画像（列表查询统治读流量且天然带校区）→ 业务隔离线与分片线重合（零跨片需求）→ 共片绑定需要公共钥匙**，最后主动交代全局统计走离线这个代价。
