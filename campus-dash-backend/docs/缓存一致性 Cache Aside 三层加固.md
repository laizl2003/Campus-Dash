## 地基：Cache Aside 本身

读写规则很简单：

- **读**：先查缓存，没有就查 DB 并回填缓存
- **写**：**先更新 DB，再删除缓存**（注意是删除，不是更新缓存）

文档第 749-752 行对比过三种策略，淘汰另外两种的原因：

| 策略 | 死因 |
|---|---|
| 更新 DB + 更新缓存 | 两个并发写，DB 和缓存的两次写入顺序可能不一致，最终 DB 是 B、缓存却是 A |
| 先删缓存 + 更新 DB | 删完缓存、DB 还没更新的间隙，一个读请求把**旧值**重新加载进缓存，之后长期不一致 |

但 Cache Aside 也不是绝对安全，它有一个理论上的极小并发窗口：

> 读请求在 DB 更新**之前**查到了旧值（此时还没写回缓存），写请求更新 DB、删了缓存，读请求才慢吞吞地把**旧值**写进缓存 → 缓存里留下脏数据。

这个窗口要求"读比写还慢"，概率极低，但不能假装不存在——于是叠三层加固，每层堵一个洞：

## 第一层：延迟双删（堵并发窗口）

写路径变成：更新 DB → 删缓存 → **延迟 500ms 再删一次**。

第二次删除就是冲着上面那个窗口去的：就算旧值被慢读请求回填了，500ms 后这一删也会把它清掉，下次读自然加载新值。实现细节是延迟用 **MQ 延迟消息**做，而不是 `Thread.sleep(500)`——sleep 会把接口线程占住 500ms，高并发下线程池直接被打满。

## 第二层：TTL 兜底（堵一切意外）

所有缓存都设过期时间（任务详情 10 分钟）。

这层防的不是某个具体并发场景，而是**所有没想到的意外**：删缓存的 MQ 消息丢了、双删都失败了、代码 bug……无论脏数据怎么进来的，最多存活 10 分钟就自动蒸发。文档里那句评价很实在："最朴素也最有效的一道保险"。

## 第三层：binlog 修正（最终修正者，本项目有变化）

原设计：用 Canal 订阅 MySQL binlog，DB 每变一次，就异步地再删/刷一次对应缓存——相当于一个独立于业务代码的"第三方监工"，业务代码里的删除逻辑全失效了它也能修正。

但注意文档第 758-759 行：**P4 期把 Canal 摘除了**（任务列表不再走 ES 检索，Canal 失去存在理由），这一层改由**一致性校验 job** 替代——每 5 分钟抽样比对 DB 和缓存，发现不一致主动修正。所以严格说现在实际生效的是"双删 + TTL + 校验 job"。

## 一句话总结

三层是**递进关系**：延迟双删主动堵已知的并发窗口 → TTL 被动兜住一切未知意外 → binlog/校验 job 作为独立于业务代码的最终修正者。前两层成本几乎为零必上，第三层看项目复杂度选配。面试被问到"Cache Aside 就够了吗"，按这个"一个窗口 + 三道保险"的结构答即可。

# 举个具体的例子
好，用一个完整的故事走一遍。人物：发单人小王、任务 1001"东区快递站取包裹"。

## 背景设定

- 任务 1001 的赏金原本是 **8 元**，Redis 里缓存着 `task:1001 = {赏金: 8}`，TTL 10 分钟
- 小王嫌没人接单，把赏金改成 **12 元**

## 事故现场：脏数据是怎么进来的

假设 10:00:00 这一刻，缓存刚好过期了（空），两个请求几乎同时到达：

| 时刻 | 读请求 A（学生刷任务详情） | 写请求 B（小王改赏金） |
|---|---|---|
| 10:00:00.000 | 缓存 miss，去查 DB | |
| 10:00:00.005 | 从 DB 读到旧值：**赏金 8** | |
| 10:00:00.010 | （突然遭遇一次 Young GC，线程卡住） | 更新 DB：赏金 8 → **12** ✅ |
| 10:00:00.020 | | 删除缓存（缓存本来就是空的，删了个寂寞） |
| 10:00:00.030 | GC 结束，把旧值 **8** 回填进缓存 | |

**结局**：DB 里是 12，缓存里是 8。之后所有学生刷到的都是"赏金 8 元"，跑腿小李看到 8 元不想接，小王明明出了 12 元却没人接单——而且这个错误会**持续整整 10 分钟**，因为缓存一旦回填，Cache Aside 的读路径再也不会碰 DB。

这就是那个"要求读比写慢"的窗口：A 只需要慢 20ms（一次 GC、一次网络抖动就够了），事故就成立。

## 第一层加固救场：延迟双删

写请求 B 改成这样：

```
10:00:00.010  更新 DB：赏金 12
10:00:00.020  第一次删缓存
10:00:00.021  发一条 500ms 的 RocketMQ 延迟消息（接口立刻返回，不 sleep）
10:00:00.030  读请求 A 回填旧值 8 ← 脏数据还是进来了
10:00:00.520  延迟消息到期，消费者执行第二次删除 → 旧值 8 被清掉 ✅
10:00:00.530  下一个读请求 miss，从 DB 加载 12，缓存恢复正确
```

脏数据只存活了 490ms，业务无感。注意 0.030 那一刻第一层**拦不住**——它不是预防，是"事后 500ms 内必清扫"。

## 第二层救场：万一延迟消息丢了呢

接着演：假设 10:00:00.021 那条延迟消息因为 MQ 故障**压根没投递**，第二次删除永远不会发生，旧值 8 又赖在缓存里了。

这时 TTL 出场：

```
10:10:00  缓存 key 到期自动蒸发
10:10:01  下一个读请求 miss → 查 DB → 加载 12 ✅
```

不需要任何人介入，最坏情况脏数据存活时间被锁死在 10 分钟。这就是"最朴素的保险"——它不针对某个具体 bug，**任何**没想到的故障（消息丢了、删除接口报错、代码写错）最终都被它兜住。

## 第三层救场：万一连删除代码都有 bug

再极端一点：新来的同学改代码，把写路径里的"删缓存"整行误删了。此时双删不存在、TTL 前 10 分钟全是脏的，而且**每次过期回填后又是脏的循环**吗？不会——过期后读请求会重新从 DB 加载正确值。但如果某个热点 key 永远不过期、或者 TTL 被设得很长，就需要一个独立于业务代码的监工：

- **原设计（binlog）**：Canal 监听 MySQL，看到 `task 表 1001 行被 update` 就主动删对应缓存——业务代码全写错了它也照样修正，因为它根本不看业务代码，只看数据库变更
- **本项目 P4 之后**：Canal 摘除了，换成一致性校验 job——每 5 分钟抽样一批任务，比对 `缓存值 vs DB 值`，发现 `task:1001` 缓存是 8、DB 是 12，主动删缓存修正

## 三层分工一句话

| 层 | 在故事里干了什么 | 防的是 |
|---|---|---|
| 延迟双删 | 500ms 后清掉 A 回填的旧值 8 | 已知的并发窗口 |
| TTL | 10 分钟后旧值自动蒸发 | 延迟消息丢失等一切意外 |
| binlog / 校验 job | 业务代码删缓存的逻辑整个失效时仍能修正 | 代码 bug、未知故障路径 |

每一层都假设"上一层可能失败"，这就是"加固"的含义——不是三个重复的保险，而是三道防线各堵不同深度的洞。
