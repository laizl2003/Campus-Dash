# CampusDash 压测方案与容量评估

> 配套文档：[架构设计与技术选型](架构设计与技术选型.md)
> 产物位置：`项目工程/campus-dash/bench/`（`scripts/` 脚本、`profiles/` 加压档位、`reports/` 报告）

这份文档解决一个问题：**怎么让"高并发"这三个字有证据。**

简历上写"支撑 XXXX QPS"、面试说"抢单不会超卖"，如果拿不出压测报告、说不清加压模型和统计窗口，这些话在有经验的面试官面前一句都站不住。所以本项目把压测当作和写代码同等重要的交付物：每个指标都能追溯到 `bench/reports/` 里的一份报告，报告里有环境、有加压参数、有火焰图、有前后对比。

## 1 压测三条纪律

在讲工具和场景之前，先立三条规矩。这三条不遵守，压出来的数字全是废的。

### 1.1 发压端与被压端隔离

在同一台机器上跑 JMeter 和被压应用，JMeter 自己就要吃掉 1-2 个核，测出来的"应用性能"里混着发压工具的开销，而且高并发时两者互相抢 CPU，数据完全不可信。

本项目的做法：

- 理想情况：应用在一台机器，JMeter 在另一台，中间件在第三台
- 本地条件受限时：至少让 JMeter 和应用是独立进程，用 `docker stats` / `top` 分别记录两者的 CPU 占用，并在报告里显式标注"应用与中间件同机，存在资源争抢"
- 绝对不做的事：一边压测一边在同一台机器上跑 IDE、编译、其他容器

**报告里如果没写环境隔离情况，这份报告就是无效的。** 面试被问"你怎么保证压测数据准确"时，这一条是第一个要答的。

### 1.2 必须预热

JVM 有 JIT 编译、类加载、连接池懒初始化、缓存冷启动。刚启动就压，前 30 秒的数据惨不忍睹，但那不是应用的真实性能。

预热流程固定为：

```text
应用启动完成
  -> 低并发（20）跑 2 分钟，让热点方法被 JIT 编译、连接池填满、缓存预热
  -> 观察 QPS 与 P99 稳定后，才开始正式加压
  -> 正式取数时丢弃前 30 秒与最后 10 秒的数据
```

丢最后 10 秒是因为压测收尾阶段线程逐个退出，并发在下降，这段数据偏乐观。

### 1.3 只取稳态区间

一次加压的曲线大致是"爬升 → 稳态 → 收尾"。只有稳态区间的数据能用来报数。判断稳态的标准：QPS 波动在 ±5% 以内，且 P99 不再持续上升。

如果一个档位怎么都到不了稳态（QPS 持续抖动、P99 一路涨），说明这个并发已经超过系统承载能力，直接记为"超过拐点"，不要勉强取平均值当结果。

## 2 工具分工

| 工具 | 用途 | 选它的理由 |
|---|---|---|
| wrk（或 oha） | 冒烟压测、快速找并发拐点 | C 实现，单核就能打出几万 QPS，发压端自己不会先成为瓶颈；适合快速试探 |
| JMeter 5.6 | 主力场景压测：多阶段、参数化用户池、断言、聚合报告 | 生态成熟、报告完整、支持同步定时器做瞬时并发、支持分布式发压 |
| JMH | 微基准：Lua 脚本序列化、雪花 ID 生成、状态机判定 | 规避 JIT 预热与死代码消除干扰，得到方法级真实开销 |
| Arthas | 在线诊断：`trace` 方法耗时、`thread` 看阻塞、`watch` 看参数 | 不重启、不改代码就能定位到具体方法 |
| async-profiler | 火焰图：CPU 热点、锁竞争（`-e lock`）、内存分配 | 采样开销低（1-2%），能在压测中实时抓，且不受 safepoint 偏差影响 |

### 2.1 为什么两个压测工具都要

分工很明确：

- **wrk 用于探路。** 改完一版代码，想知道大概在什么并发下会崩，用 wrk 三条命令十分钟出结果。它的缺点是不好做复杂场景（参数化、多接口混合、断言）。
- **JMeter 用于出报告。** 需要"2000 线程瞬时释放"这种精确控制、需要每个线程用不同的用户 token、需要断言"响应里 success 字段必须为 true"，这些只有 JMeter 方便做。

典型 wrk 命令：

```bash
# 12 线程、400 连接、压 60 秒，用 lua 脚本带 token 和随机 taskId
wrk -t12 -c400 -d60s --latency \
    -s bench/scripts/grab.lua \
    http://127.0.0.1:8080/api/errands/grab
```

### 2.2 为什么需要 JMH

有些优化的效果太小，在接口级压测里会被网络和数据库开销淹没。比如"雪花 ID 生成用 synchronized 还是 CAS"、"Lua 脚本参数用 JSON 还是拼字符串"，这类差异在微秒级，只有 JMH 能测出来。

用 JMH 的场合：纯 CPU 计算、无 IO、耗时在微秒到毫秒级的方法。用错场合（比如拿 JMH 测带数据库的方法）会得到方差极大的垃圾数据。

## 3 六类压测场景

| 编号 | 场景 | 加压模型 | 核心观测 | 通过标准 |
|---|---|---|---|---|
| S1 | 单任务尖峰抢单（N 抢 1） | 1 个任务，2000 线程用同步定时器瞬时释放 | 成功数、超卖数、重复抢数、P99 | 成功数严格等于名额数，超卖与重复抢均为 0 |
| S2 | 抢单接口持续吞吐 | 多任务混合，阶梯加压 100→200→400→800→拐点 | QPS、P95/P99/P999、错误率、CPU、GC、连接池等待 | 错误率 < 0.1%，拐点前 P99 达标 |
| S3 | 读多写少混合 | 任务列表/详情读 : 抢单写 = 9 : 1 | 缓存命中率、DB QPS 降幅、ES 查询耗时 | 缓存命中率达标，DB 未被打穿 |
| S4 | 资金结算吞吐 | 并发结算 + 同时跑对账 job | 结算 TPS、行锁等待、死锁数、借贷平衡 | 零资金差异、无死锁 |
| S5 | 延迟流转准时性 | 1 万条 LOCKED 任务同一秒集中到期 | 流转准时率、误差分布、消息堆积深度 | 误差 P99 < 1s，零重复流转 |
| S6 | 故障注入压测 | 压测中注入 Redis 抖动/主从切换、MySQL 慢查、MQ 堆积 | 降级是否生效、是否出现超卖或资金差异 | 降级正确，数据零错误 |

### 3.1 S1：单任务尖峰抢单

这是全项目最重要的一个场景，它验证的是正确性而不是性能。

**加压模型**：JMeter 用 `Synchronizing Timer`，把 2000 个线程全部阻塞住，凑齐 2000 个后同时释放。这比"2000 线程逐个启动"更接近真实的秒杀式抢单，也更容易暴露并发 bug。

```text
Thread Group: 2000 线程，ramp-up = 0，循环 1 次
  └── Synchronizing Timer: Number of Simultaneous Users = 2000
      └── HTTP Request: POST /api/errands/{id}/grab
          ├── CSV Data Set: 2000 个不同用户的 token
          └── Response Assertion: 断言 code ∈ {SUCCESS, SLOT_FULL, ...}
```

**验证方式**（这是重点，不能只看 JMeter 报告）：

```sql
-- 1. 抢中人数必须等于名额数（INV-1）
SELECT COUNT(*) FROM grab_record WHERE errand_id = ? AND result = 'GRABBED';

-- 2. 不能有同一用户占多个名额（INV-2）
SELECT runner_id, COUNT(*) c FROM grab_record
 WHERE errand_id = ? AND result='GRABBED' GROUP BY runner_id HAVING c > 1;

-- 3. 任务状态与抢中记录必须自洽
SELECT status, grabber_id, slot_taken FROM errand WHERE id = ?;

-- 4. Redis 名额与 DB 必须一致（检查名额泄漏）
--    GET errand:slot:{id} 应等于 slot_total - slot_taken
```

四条全过才算通过。**只看 JMeter 的"成功响应数 = 1"是不够的**——可能 DB 里写了两条但其中一条响应超时了，客户端视角看只有一个成功。所以必须回到数据库验证。

**故意制造失败来验证测试有效性**：把 Lua 脚本换成"先 GET 再 DECR"的错误实现，重跑 S1，必须能压出超卖。如果压不出来，说明加压模型不够狠（并发不足或没用同步定时器），测试本身是无效的。这一步在教程里一定要做，它证明了"没测出问题"是真的没问题，而不是测试太弱。

### 3.2 S2：抢单接口持续吞吐

这是产出 QPS 数字的主场景。

**阶梯加压**，每档稳定 3 分钟：

| 档位 | 并发 | 记录项 |
|---|---|---|
| 1 | 100 | QPS、P95、P99、P999、错误率、CPU%、GC 次数与总时长、Hikari 等待数、Redis OPS |
| 2 | 200 | 同上 |
| 3 | 400 | 同上 |
| 4 | 800 | 同上 |
| 5 | 1600 | 同上 |
| ... | 直到出现拐点 | 同上 |

**拐点判定规则**（写进报告，不靠感觉）：

```text
出现以下任一情况，判定为已越过最佳并发点：
  1. 并发翻倍，QPS 增幅 < 10%
  2. 并发翻倍，P99 翻倍以上
  3. 错误率 > 0.1%
  4. CPU 已达 90%+ 且 QPS 不再上升
```

拐点前的最后一档，才是可以写进简历的"单机 QPS"。**很多人报的是"压崩前的最大 QPS"，那个数字对应的 P99 往往已经好几秒，没有实际意义。**

### 3.3 S3：读多写少混合

真实流量是读远多于写，纯写压测会高估数据库压力、低估缓存作用。

**混合比例 9:1**（列表和详情读 90%，抢单写 10%），三种配置对比：

| 配置 | DB QPS | 接口 P99 | 说明 |
|---|---|---|---|
| 无缓存 | `[待补充]` | `[待补充]` | 基线，所有读都打 DB |
| Redis 缓存（Cache Aside） | `[待补充]` | `[待补充]` | 分布式缓存的收益 |
| Redis + 热 Key 分片打散 | `[待补充]` | `[待补充]` | 单个爆款 key 拆成 N 份副本后的额外收益 |

这张表回答两个面试问题：“缓存带来了多少收益”和“不加本地缓存、热 Key 靠什么扛”。它同时也是“到底要不要引入本地缓存”的决策依据：只有当 Redis CPU 跑满、OPS 触顶而应用 CPU 仍有余量时，才考虑加本地缓存（参见架构文档 9.3）。本项目默认不加。

### 3.4 S4：资金结算吞吐

资金场景的压测重点不是 TPS 高低，而是**高并发下钱有没有算错**。

**加压模型**：500 并发对不同任务做结算，同时后台跑对账 job（模拟真实的读写混合）。

**必须验证**：

```sql
-- 借贷平衡：全表借贷必须相等
SELECT SUM(CASE WHEN direction='DEBIT' THEN amount ELSE 0 END) AS debit,
       SUM(CASE WHEN direction='CREDIT' THEN amount ELSE 0 END) AS credit
  FROM wallet_ledger;

-- 快照一致：账户余额必须等于流水净额
SELECT a.id, a.available + a.frozen AS snapshot, IFNULL(l.net, 0) AS ledger_net
  FROM wallet_account a
  LEFT JOIN (SELECT account_id,
                    SUM(CASE WHEN direction='CREDIT' THEN amount ELSE -amount END) net
               FROM wallet_ledger GROUP BY account_id) l
    ON l.account_id = a.id
 WHERE a.available + a.frozen <> IFNULL(l.net, 0);

-- 死锁次数
SHOW GLOBAL STATUS LIKE 'Innodb_deadlocks';
```

第二条查询返回任何行都是致命 bug。这个场景的通过标准是**零容忍**，不存在"差 1 分钱可以接受"。

另外要专门测**并发结算同一任务**：200 个线程同时对同一个任务发结算请求，验证 `biz_no` 唯一索引的幂等性——最终只能有一组流水，跑腿的余额只能增加一次。

### 3.5 S5：延迟流转准时性

**加压模型**：造 1 万条 `LOCKED` 状态任务，`locked_at` 全部设为同一秒，让它们在同一时刻集中到期。这模拟的是"某个热门时段大量任务同时超时"的最坏情况。

**记录方式**：每条任务记录 `期望流转时间`（locked_at + 5min）和 `实际流转时间`（status_log 里的时间戳），算差值分布。

| 指标 | 口径 | 目标 |
|---|---|---|
| 流转准时率 | 误差 < 1s 的比例 | `[待补充]` |
| 误差 P99 | 差值的 P99 | < 1s |
| 误差最大值 | 最坏情况 | `[待补充]` |
| 重复流转数 | 同一任务同一轮被流转两次的数量 | 必须为 0 |
| MQ 堆积峰值 | 消费堆积深度 | `[待补充]` |

集中到期会造成 MQ 瞬时堆积，如果消费者处理不过来，准时率就掉了。所以这个场景还要测"消费者并发度调到多少才能满足准时率"，这是容量规划的一部分。

### 3.6 S6：故障注入压测

前五个场景测的是"正常情况下性能如何"，这个场景测"出问题时会不会错"。它是最容易被忽略、但面试价值最高的场景——**面试官问"Redis 挂了怎么办"，有实测数据的回答和纯理论的回答完全是两个层次。**

| 注入故障 | 注入方式 | 期望行为 | 绝对不能发生 |
|---|---|---|---|
| Redis 完全不可用 | `docker pause redis` | 抢单快速失败或降级到纯 DB CAS 模式，接口不雪崩 | 超卖 |
| Redis 主从切换 | 手动 failover | 短暂失败后恢复，名额可能被短暂判错 | 超卖（DB 唯一索引兜住） |
| Redis 网络抖动 | `tc netem` 加 200ms 延迟 | P99 上升但不超时雪崩，熔断按预期触发 | 线程池被打满导致整个应用挂 |
| MySQL 慢查询 | 注入 `SELECT SLEEP(3)` 占满连接 | Sentinel 熔断，快速失败 | 连接池耗尽导致所有接口挂 |
| MQ 不可用 | `docker pause rocketmq` | 本地消息表堆积 PENDING，恢复后自动补发 | 消息永久丢失、任务永久卡 LOCKED |
| worker 进程被杀 | `kill -9` | 重启后从消息表/ZSET 恢复未处理任务 | 资金卡在冻结状态无人处理 |

每种故障注入后都要跑一遍 S1 和 S4 的数据校验 SQL。**"降级了"不代表"对了"**，降级后数据依然必须正确。

## 4 容量评估

### 4.1 用 Little's Law 反推配置

```text
并发数 = QPS × 平均响应时间
```

举例：目标 1000 QPS，平均响应时间 20ms，则系统内同时在处理的请求数 = 1000 × 0.02 = 20 个。这个数字直接决定线程池和连接池怎么配。

反过来用：如果 Tomcat 线程池只有 200，而平均响应时间是 500ms，那理论 QPS 上限 = 200 / 0.5 = 400，再怎么加压也上不去。这时候要做的不是加线程，而是**降低响应时间**。

### 4.2 连接池不是越大越好

常见错误是"QPS 上不去就加大连接池"。实际上连接池超过一定值后 QPS 会下降，因为数据库的并发处理能力有限，更多连接只会加剧锁竞争和上下文切换。

参考公式（HikariCP 官方建议）：

```text
maxPoolSize ≈ CPU 核数 × 2 + 有效磁盘数
```

4 核机器大概是 10 左右。这个数字通常让人难以置信（"才 10 个连接怎么支撑 1000 QPS？"），但配合 Little's Law 就清楚了：如果单条 SQL 耗时 5ms，10 个连接理论上能支撑 10 / 0.005 = 2000 QPS。

教程里要做一组实测：连接池设 10 / 50 / 100 / 200，压同一个档位，画出 QPS 曲线。大概率会看到 50 之后 QPS 不升反降。**这组数据比任何理论解释都有说服力。**

### 4.3 容量结论表

压测完成后填这张表，它是"这个系统能扛多少"的最终答案：

| 项 | 值 | 依据 |
|---|---|---|
| 单机最佳并发 | 400（默认配置稳定线） | P7 S2：400 并发 0 错误；800 默认配置出现 146 IOException |
| 单机安全 QPS（拐点前一档） | 6455 QPS @400 并发 | P7 S2 报告，每档 60s，同机 |
| 对应 P99 | 151ms @400 并发 | P7 S2 报告，每档 60s，同机 |
| 零超卖可承受瞬时并发 | ≥2000 | S1 报告，应用层与 DB 双验证 |
| 结算 TPS | ≈191 | S4 报告，同机 64 线程关 MQ |
| 单实例 WebSocket 连接上限 | `[待补充]` | 长连接压测 |
| 支撑 1 万在线用户需要的实例数 | `[待补充]` | 按安全 QPS 反推 |

## 5 六轮调优迭代记录

这是教程 09 篇和面试答辩的核心叙事。每轮固定四列：瓶颈现象 → 定位手段 → 优化动作 → 前后对比。

| 轮次 | 瓶颈 | 定位手段 | 优化动作 | QPS 前→后 | P99 前→后 |
|---|---|---|---|---|---|
| R1 | 基线版（无缓存 + `SELECT FOR UPDATE`）QPS 极低，大量锁等待 | `SHOW ENGINE INNODB STATUS` 看锁等待队列 + Arthas `trace` | 改 Redis Lua 原子抢单 | `[待补充]` | `[待补充]` |
| R2 | 瓶颈转移到 Redis 单连接串行 | Redis `SLOWLOG` + Redisson 连接池监控 | 连接池扩容 + pipeline 批量 | `[待补充]` | `[待补充]` |
| R3 | 瓶颈转移到 Tomcat 线程与 DB 落库 | 线程 dump（大量 WAITING on Hikari）+ 连接池等待队列指标 | 线程池隔离：抢单/查询/结算三池 | `[待补充]` | `[待补充]` |
| R4 | 同步落库拖慢抢单响应 | async-profiler 火焰图，落库占总耗时 60%+ | 抢中后 MQ 异步落库 | `[待补充]` | `[待补充]` |
| R5 | 平台线程池在 IO 密集下利用率不足 | 两版实测对比（线程数 vs 吞吐曲线） | JDK 21 虚拟线程改造 | `[待补充]` | `[待补充]` |
| R6 | P99 出现规律性毛刺 | GC 日志（每 30s 一次 200ms 停顿）+ 日志同步写阻塞 | G1→ZGC 调参 + Logback AsyncAppender | `[待补充]` | `[待补充]` |

### 5.1 每轮必须留下的证据

只填数字不够，每轮要在 `bench/reports/` 留下：

1. 压测报告（含加压参数，保证可复现）
2. 瓶颈证据截图或文本（火焰图、线程 dump 片段、`SHOW ENGINE INNODB STATUS` 关键段、GC 日志片段）
3. 优化前后的代码 diff 说明（改了什么、为什么这么改）
4. 副作用说明（比如 R4 的异步落库牺牲了什么一致性、怎么补的）

第 4 点最容易被跳过，但面试官最爱问。R4 的异步落库把"抢单成功"和"数据库有记录"之间变成了最终一致，代价是极端情况下用户看到"抢单成功"但刷新后消失。所以真实落地时要么保留同步落库，要么用"抢单成功但状态为 PENDING_CONFIRM"的中间态。**教程里要明确写出这个取舍，不能只报喜不报忧。**

### 5.2 R5 虚拟线程的正确预期

虚拟线程不是万能加速器。它的收益来自"阻塞时不占平台线程"，所以：

- **IO 密集（本项目的抢单：Redis + MySQL 调用）**：收益明显，能用少量平台线程支撑大量并发请求
- **CPU 密集**：几乎没有收益，甚至因为调度开销略有下降
- **有 `synchronized` 阻塞的代码路径**：JDK 21 里 `synchronized` 内的阻塞会 pin 住载体线程，收益被抵消（JDK 24 改进了这点）

所以 R5 的实测要同时给出"哪些接口提升明显、哪些没提升"，并说明原因。面试时能讲清"虚拟线程在什么场景下没用"，比只会说"虚拟线程很快"强得多。

## 6 观测联动

**没有看板的压测等于瞎压。** QPS 上不去时，如果不能立刻判断瓶颈在应用还是中间件，就只能靠猜。

压测期间 Grafana 必须同屏显示以下面板：

| 分组 | 指标 | 用途 |
|---|---|---|
| 接口层 | QPS、P95/P99/P999、错误率、限流拒绝数 | 判断整体表现与是否触发限流 |
| Tomcat/线程 | 活跃线程数、队列长度、拒绝数 | 判断是否线程池打满 |
| 连接池 | 活跃连接、等待线程数、等待时长 | 判断是否卡在拿连接（最常见的伪 DB 瓶颈） |
| JVM | 堆使用、GC 次数与停顿时长、虚拟线程数 | 判断 P99 毛刺是否来自 GC |
| Redis | OPS、命中率、慢查询数、连接数 | 判断 Lua 脚本或大 key 问题 |
| MySQL | QPS、行锁等待、慢查询数、活跃线程 | 判断锁竞争与索引问题 |
| RocketMQ | 生产/消费 TPS、堆积深度、重投次数 | 判断消费能力是否跟得上 |
| 业务指标 | 抢单成功率、超卖计数（必须恒为 0）、流转准时率 | 性能与正确性同时看 |

最后一行的"超卖计数"是这个项目独有的设计：把 INV-1 做成一个实时指标上报，压测中一旦不为 0 立即告警。**把正确性做成可监控指标，而不只是测试断言**，这是能明显区分工程成熟度的做法。

## 7 压测数据准备与清理

### 7.1 造数规模

| 数据 | 规模 | 用途 |
|---|---|---|
| 用户 | 1 万（含 token 预生成） | S1/S2 的并发用户池 |
| 任务 | 10 万（分布在 5 个校区，多种状态） | S2/S3 的随机访问目标 |
| 钱包账户 | 1 万，每个初始余额 10000 元 | S4 结算压测 |
| LOCKED 任务 | 1 万，locked_at 集中在同一秒 | S5 延迟流转压测 |

### 7.2 数据隔离约定

**所有压测数据带 `bench_` 前缀标记**，绝不与业务数据混用：

- 用户 `nickname` 以 `bench_` 开头
- 任务 `title` 以 `bench_` 开头
- 清理脚本按前缀删除，不会误删正常数据

清理脚本必须做到：`bench_cleanup.sh` 执行后，`errand`、`grab_record`、`wallet_ledger`、`local_message` 里的压测数据全部清除，Redis 里 `errand:*` 的压测 key 全部删除，ES 索引里的压测文档全部删除。

**为什么强调这个**：压测数据不清理会污染后续压测（比如上一轮遗留的 `LOCKED` 任务被这一轮的超时扫描捞出来处理），导致数据无法复现。

### 7.3 加压档位配置化

所有加压参数进 `bench/profiles/`，例如：

```yaml
# bench/profiles/s2-throughput.yaml
scenario: S2-抢单接口持续吞吐
warmup:
  concurrency: 20
  duration: 120s
steps:
  - { concurrency: 100,  duration: 180s }
  - { concurrency: 200,  duration: 180s }
  - { concurrency: 400,  duration: 180s }
  - { concurrency: 800,  duration: 180s }
  - { concurrency: 1600, duration: 180s }
sampling:
  discard_head: 30s
  discard_tail: 10s
assertions:
  error_rate_max: 0.001
  oversold_count: 0
```

有了这个文件，任何人都能按同一档位复现任何一份报告。报告里必须引用它用的是哪个 profile。

## 8 压测报告模板

报告落在 `bench/reports/report-YYYYMMDD-HHMMSS.md`，命名法与 `globex-agent/eval/report-*.md` 一致。固定结构：

```markdown
# 压测报告 YYYYMMDD-HHMMSS

## 1 环境
- 应用：JDK 21 / Spring Boot 3.3 / 4C8G / 单实例
- 中间件：MySQL 8.0.x / Redis 7.x / RocketMQ 5.x / ES 8.x（部署方式：docker-compose）
- 隔离情况：[应用与中间件同机 / 分离]，发压端独立
- 代码版本：commit hash
- 加压档位：bench/profiles/xxx.yaml

## 2 场景与目标
场景编号 S?，本轮想验证什么、对应哪一轮调优（R?）

## 3 结果
| 并发 | QPS | P95 | P99 | P999 | 错误率 | CPU% | GC 停顿 |
|---|---|---|---|---|---|---|---|

## 4 正确性校验
四条校验 SQL 的执行结果（超卖数、重复抢数、借贷平衡、快照一致）

## 5 瓶颈分析
火焰图 / 线程 dump / 慢日志证据 + 结论

## 6 结论与下一步
拐点判定结果、本轮是否达标、下一轮要改什么
```

**第 4 节（正确性校验）不允许省略。** 性能数据再好，如果超卖了，这份报告的结论就是"失败"。

## 9 从压测数据到简历表达

压测的最终目的之一是产出可辩护的简历指标。转化时守三条：

1. **带环境**：不写"支撑 5000 QPS"，写"4C8G 单机、MySQL 8 + Redis 7 环境下，抢单接口稳态 QPS `[待补充]`、P99 `[待补充]`ms"
2. **带口径**：不写"性能提升 10 倍"，写"通过 Lua 原子抢单替换数据库悲观锁等六轮优化，同并发档位下 QPS 从 `[待补充]` 提升至 `[待补充]`"
3. **带正确性**：并发指标必须配一个正确性指标，"2000 瞬时并发下零超卖、零重复抢"比单纯的 QPS 更能体现功底

反面例子：简历写"高并发场景 QPS 10 万+"，面试官一问"什么机器、什么接口、P99 多少、怎么测的"就答不上来，这条指标会变成负分项。**宁可数字小一点，也要每个数字都能追溯到一份报告。**
